## Why

功能表（服务场景）由 AI 语义归纳，**缺乏形式与类别约束时每轮结果都不同**，且易退化成技能属性清单。

实证（同一被测技能连续三轮）：

| 轮次 | 功能表实际内容 |
|---|---|
| v8 | 按功能分 5 条（数据库列表 / Schema / 表 / 字段 / 字段关系查询） |
| v9 | 按**属性**分 6 条（服务场景 / 输入参数 / 输出格式 / 交互方式 / 依赖脚本 / 支持数据库类型） |
| v10 | 又是属性分 6 条，且与 v9 措辞不同 |

读者无法从中得知「能用它做什么」。同时 `task_map`（服务场景 → 功能任务映射）连续两轮为 `None`，导致基准报告 §4 渲染成「总览 + 验证」两张割裂的表。

**关键结论**：依赖 AI 自觉遵守提示词要求不可靠——已写明的口径（正例、禁止清单、JSON 示例）连续两轮未被遵守。必须改为机器可判的形式约束 + 门禁阻断。

## 被否决的方案（留档，避免重提）

**「脚本预填候选」**（依据被测技能的 `query_*.py` 推导服务场景）曾被提出，经评审否决：

- **层级错配**：外调脚本是**实现机制**，服务场景是**用户意图**；多个脚本的组合才构成一个场景，反之不成立
- **过度拟合**：仅在"功能与脚本一一对应"的单一技能上吻合，未验证第二个技能
- **定制风险**：对无脚本的纯指引型技能完全失效，违反"不为特定被测技能定制"

现有 `auto_subjective._advisory_function_table()` **刻意只提供语义材料**（frontmatter description → When to Use → 过程中的服务声明），不预填结论——该设计正确，应保留。

## 任务类别判定

- 判据：是否改变对外可观察行为 → **是**（改变功能表呈现与门禁阻断条件）
- 分流：**行为变更**，任务态由本变更承载，不登记进任务记录

## 历史错误（ERR 编号）

无。

## What Changes

| # | 变更 | 优先级 |
|---|---|---|
| F1 | 形式约束：功能表须为列表（每条 `-` 开头） | P0 |
| F2 | 类别约束：禁止属性/实现机制类表述（输入参数、输出格式、依赖脚本、适用范围、交互方式、实现机制、模块、架构等） | P0 |
| F3 | **主语约束**：每条须以「客户 / 用户 / 使用者」为主语造句——把视角钉在使用者，而非内部流程 | P0 |
| F4 | 一致性约束：`task_map` 必填，且须覆盖每条服务场景；缺失即阻断 | P0 |
| F5 | 字面换行归一化：`\\n`（字面反斜杠 n）还原为真换行——否则整表被当成一条，逐条校验失效 | P0 |
| F6 | 依据标注：每条须注明 SKILL.md 出处 | P1 |
| F7 | 门禁接入：`check_stage0_dod.py` 校验功能表与 task_map，不合规与「未裁定」同等阻断 | P0 |

**约束边界**：以上均只约束**形式与语义类别**，不约束"这个技能有哪些功能"，故不构成对特定技能的定制。

## Non-goals（本次不做）

- 功能清单中内部策略文本的过滤（如「快速通道策略」，属样本抽取质量，另立）
- 依赖标识显示真实地址（另立）
