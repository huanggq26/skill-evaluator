## Why

阶段 0 静态评测报告与最后阶段两份报告在**真实评测运行**中暴露出一批「看起来生成成功、实则结论失真」的缺陷。与 2026-09-18 那批（格式派生、级别文本化）不同，本批缺陷的共性是：**产物文件正常生成、校验通过、流水线退出码 0，但报告内容错误或缺失**。

两轮真实运行（win / opencode）的实测证据：

| # | 现象 | 实测证据 |
|---|---|---|
| 1 | 关键问题汇总**从未真正汇总** | `report_data.json` 中 `objective_critical` 有 9 行、`objective_warning` 有 9 行，报告却显示「无」——模板标注为 `field`（渲染只读 `text`）而数据存放在 `rows`，永远读不到 |
| 2 | 主观槽位未裁定却照常出报告 | v4 运行 28 个槽位中 15 个为空；流水线仍打印「✅ 开始阶段测评完成」并自动接续阶段 1–4 |
| 3 | 同一任务在报告内**自相矛盾** | §4.2 表格写「本次未完成评测（评测侧限制，非技能缺陷）」，§4.3 却写「❌ 技能未能交付该能力」 |
| 4 | BOM 导致 frontmatter 误报为严重缺陷 | `extract_stats.json` 中 `frontmatter = None`（SKILL.md 带 UTF-8 BOM → YAML 解析失败），下游判为「缺少必需字段 name/description」并标严重 |
| 5 | 依赖探测方法不匹配 | 8 项依赖中 6 项 GET 返回 405，同一主机 `db_list` 用 GET 返回 200——端点可达，实为方法不匹配；曾误判为技能契约缺陷并触发否决 |
| 6 | 主观裁定写入格式不受约束 | AI 填写的 rows 使用 `问题/原因/位置` 而非模板列 `位置/原因/改进建议`，导致原因列显示裸级别词「警告」、改进建议列空白；`modalities` 被填成字面值 `text` |
| 7 | Windows 环境不可用 | runner 内 35 处写死 `python3`（Windows 无此命令）→ 全流程第一步失败；PowerShell 重定向产出带 BOM 的 JSON → 下游 `json.load` 解析失败 |
| 8 | 重跑残留导致「同一评测两份结论」 | v4 目录下 `quality/`（旧版技能产出）与 `table_column_relations/quality/`（新版）并存，两者标题与呈现格式不同 |

## 任务类别判定

- 判据：是否改变对外可观察行为 → **是**（改变报告内容、汇总结果、判定归类、门禁行为、退出码）
- 分流：**行为变更**，任务态由本变更承载，不登记 TASKLOG（依 `openspec/config.yaml` 无双写纪律第 5 条）

## Non-goals（本次不做）

- 交互式 CLI 技能的执行能力。被测技能为交互式（需用户逐步输入参数），评测器无法自动执行 → 全部任务 `unsupported`。这是**能力缺口**而非缺陷，需单独立项设计，本次仅在呈现上如实标注为「未实测」。
- `assemble_findings.py` 的完整模板化（改为读取 `assets/problem_report.template.md`）。本次仅修正硬编码标题。
- 样本设计缺陷治理（功能任务可被裸 Agent 直接调 API 完成、测不出技能增量价值）。
