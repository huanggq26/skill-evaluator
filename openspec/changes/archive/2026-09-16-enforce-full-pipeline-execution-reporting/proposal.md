# 强制完整执行与阶段告知

## Why

在跨环境（Windows + opencode）与内部机器两处实测中，暴露出同一根源的三类实证缺陷：

1. **阶段 0 完成后停下却不告知**：仅输出"报告位置"一句，未说明"这仅是阶段 0（预检）"、未列该阶段完整产物、**未给出继续执行的命令**，用户无从得知需要确认或如何继续。
2. **全流程终态无交付说明**：阶段 4 聚合完成只给出产物**目录**，无"全部阶段完成"提示、无最终交付物文件名与路径清单；既有的完成清单面向 AI 自查，不面向用户。
3. **主观推断导致阶段跳过**：评测内部技能时，Agent 见内部域名（`…paasuat.cmbchina.cn`）便**推断**"评测环境不可达"，**未执行 0B 探测**、**未尝试执行**，直接跳过阶段 2/3/4，且**未告知用户**——而实测该 API 在本环境可访问，属误判。评测因此退化为静态分析，失去"基准评测"的意义。

三者同源：评测执行的**完整性**与**透明性**缺少可执行约束，且缺少可验证的门禁来兜底。

## What Changes

- **新增 capability `pipeline-execution-integrity`**：禁止未实测的不可达推断、执行尝试强制、阶段过渡强制、阶段完成与终态的告知契约、全流程请求的模式选择。
- **修改 capability `dependency-availability`**：补"探测结果的阻断边界"——只有契约型缺陷阻断，环境/瞬态与配置待补仅记录并继续执行阶段 1→4（**澄清消费规则，不改探测判定逻辑**）。
- **规范层**：`SKILL.md` 增执行纪律与模式路由约束、交互闸门补告知四项；`references/dependency_availability.md`、`exec_common.md`、`stage1/2/3` 补对应硬约束与前置条件。
- **脚本层**：阶段结束统一输出"进度 / 产物清单（含绝对路径）/ 下一步命令 / 停下时指明看什么与做什么"；仅开始阶段模式补继续命令；终态补**交付物清单**——含最终交付物（文件名 + 路径）**与阶段卡点中间产物**（中间产物是流程逐级执行的保证，缺失即判定流程未完整执行）；中间产物缺失须显式报错而非静默结束。
- **推进机制**：以"可用性探测结果驱动推进"的推理链替代执行者主观判断（探测可达→继续执行；环境/配置类失败→记录并继续；契约型缺陷→阻断；未探测→禁止推断），使"是否继续"成为确定性链条而非主观决策。
- **判定修正（BREAKING）**：鉴权类失败（**401/403**）由契约型缺陷改判为**配置待补**——不计入失败数（不拉低可用性评分）、不触发否决（不阻断全流程），仅提示补凭证后重测；其余 4xx 判定不变。此前 401/403 会被判为"技能契约缺陷"并阻断全流程，会使内部需鉴权的 API 被误拦在阶段 0。
  > 标 **BREAKING** 仅因**实际行为发生变化**（原本阻断 → 改为不阻断）；就**规范**而言本项属**纠偏**：DEP-AVAIL 分层中 `D1 connectivity` 只验端点存活 / 链路可达，而 401/403 恰证明链路已通；探活为匿名请求，故属既有裁决策略的 `config missing`（"需凭据但未配置"），其规定本就是**不否决、记为未配置、提示补配置**。详见 design 决策 8。

## Capabilities

### New Capabilities
- `pipeline-execution-integrity`：评测流水线必须完整执行（不得因主观推断或依赖状态跳过阶段与任务），并在每个阶段结束与全流程终态向用户明确告知进度、产物与下一步。

### Modified Capabilities
- `dependency-availability`：新增「可用性探测结果的阻断边界」需求——明确探测结果只记录依赖状态，除契约型缺陷外不阻断阶段 1→4 的执行（**澄清消费规则，不改探测判定逻辑**）。

## 本次是否触及历史错误（ERR 编号）

**触及，且属复发**：

| 编号 | 内容 | 与本次的关系 |
|------|------|--------------|
| **ERR-009** | 「约束已写但未激活」——已**第五次**出现（约束存在 ≠ 生效） | 本次为**同型第六次苗头**：0B 探测规则、阶段推进要求均已存在，Agent 仍不执行 |
| **ERR-014** | 管线跑通 ≠ 评测完成 | 本次直接复现：阶段 0 跑通即结束，评测未完成 |
| **ERR-002** | 未发现阶段 2/3 未执行 | 本次直接复现：阶段 2/3 被跳过且无提示 |

**防复发设计（关键）**：ERR-009 已五次复发，说明**"补一条文字约束"不是有效手段**。故本次不以补文字为主，而以**可验证门禁 + 产物断言**落地——阶段 2/3 未执行时最终报告须显式标注、终态须有交付物清单、中间产物缺失须报错退出，使"未完整执行"在产物上**可见、可判定**，而非依赖 Agent 自觉。

## 范围

- 执行完整性约束：禁止未实测推断、执行尝试强制、失败处理、阶段过渡强制。
- 探测结果消费规则的澄清（仅契约型缺陷阻断）。
- 阶段结束与全流程终态的告知契约（进度 / 产物清单与路径 / 下一步 / 需确认则询问）。
- 全流程请求必须执行至阶段 4 的模式路由约束。

## 非目标

- **不修改** `dep_probe` 的失败类别判定逻辑（现状已正确区分契约型/环境型/配置型，改它属过度且会动到刚归档的评分口径）。
- **不修改**评分口径、报告格式与模板字段。
- **不修改**阶段 0 既有检查项与门禁阈值。
- **不针对**单一平台（opencode / Windows）做特化——方案须跨平台通用，路径一律由运行时解析后展示。

## Impact

- 评测在依赖不可达时**仍会继续执行**，产出含失败记录的完整评测（而非退化为静态分析）。
- 用户获得的输出变长，但**进度、产物位置与下一步始终可见**。
- 阶段 2/3 未执行将在产物上显式暴露，无法再静默通过。
- 依赖返回 401/403 时**不再阻断**全流程、不再拉低可用性评分（此前会被误判为契约缺陷并否决）；仅有真实契约缺陷才会阻断。
