## Context

**现状（已核实）**：

- 探测脚本**已按失败类别区分**：契约型缺陷触发阻断/否决，环境/瞬态与配置待补**本就不否决**（代码注释与判定逻辑均已如此）。故"API 不可达 → 跳过阶段 2/3"**不是流程设计所致**，而是两件事叠加：① Agent **未执行探测**而以域名特征代替实测；② 文档**未写清**"探测结果只记录、不阻断"。
- `SKILL.md` 已有阶段 0 交互闸门与"通过时告知报告绝对路径"的义务，但**义务仅覆盖一个路径**，未要求进度、完整产物清单、下一步命令。
- 脚本侧：仅开始阶段模式结束时只输出"报告位置"一句（无下一步）；阶段 4 聚合完成只输出产物**目录**（无文件清单）；既有的"AI 评测执行者完成清单"面向 AI 自查，非用户交付说明。

**实证（本次触发）**：

1. Windows + opencode 全流程评测：阶段 0 后停下，未告知产物路径/名称与继续方式。
2. 内部机器评测 `table_column_relations`：Agent 见内部域名推断不可达，未跑 0B、未尝试执行，直接跳过阶段 2/3/4 且未告知（实测 API 可访问）。

**历史错误（决定本方案取向）**：ERR-009「约束已写但未激活」**已第五次**出现；ERR-014「管线跑通 ≠ 评测完成」；ERR-002「未发现阶段 2/3 未执行」。三者共同指向：**补文字约束无效，必须有可验证的激活机制**。

## Goals / Non-Goals

**Goals：**

- 使"依赖不可达"不再成为跳过阶段的理由，且该判断必须基于实测而非推断。
- 使阶段推进与任务执行在产物层面**可验证**：未执行即暴露，无法静默通过。
- 使每个阶段结束与全流程终态都给出：进度、产物清单（含绝对路径）、下一步命令。
- 全流程请求必须真正跑完阶段 1→4。

**Non-Goals：**

- 不改探测的类别判定逻辑与评分口径。
- 不改报告模板字段与格式。
- 不为单一平台特化处理。
- 不解决"环境限制如何计入评分"这一更深层问题（本次仅确保它被**记录在产物中**，评分口径的调整留待后续变更）。

## Decisions

**决策 1：只澄清探测结果的消费规则，不动判定逻辑**

- 理由：判定逻辑本就正确（仅契约型阻断）。改代码会动到刚归档的可用性口径，收益为负。
- 落地：在 `dependency-availability` 规范中写明"仅契约型阻断；环境型/配置型仅记录并继续执行"。

**决策 2：以可验证门禁与产物断言为主，不以补文字为主（针对 ERR-009）**

- 理由：ERR-009 已五次复发，证明"写上约束"不等于"约束生效"。
- 落地三处**在产物上可见**的判定点：
  1. 阶段 2/3 未执行时，评测产物 MUST 显式标注未执行及原因（无法再产出"看似完整"的结果）；
  2. 中间产物缺失导致最终报告未生成时，脚本**报错退出**并给出补救命令，MUST NOT 静默结束；
  3. 全流程终态须逐项列出最终交付物文件名与绝对路径（缺一即视为未完成）。

**决策 3：约束落在执行者必经路径，并向各阶段前置条件分散**

- 理由：约束写在深处等于没写。
- 落地：`SKILL.md` 执行纪律写总纲（禁止未实测推断、尝试优先、阶段过渡强制）；`exec_common.md` 写执行与失败处理硬约束；`stage1/2/3` 前置条件各自声明"上一阶段未完整执行不得作为跳过本阶段的理由"。

**决策 4：保留"仅开始阶段"模式的语义，但禁止静默停下**

- 理由：该模式（快速预检）有真实价值，不应取消；问题在于停下时不说下一步。
- 落地：结束时 MUST 输出"仅完成阶段 0（预检）+ 继续全流程的具体命令"。

**决策 5：模式路由约束**

- 理由：用户说"全流程"却停在阶段 0，说明模式选择缺少约束。
- 落地：`SKILL.md` 明确"全面/全流程/完整评测"表述对应必须执行至阶段 4 的模式。

**决策 6：路径一律运行时解析后展示，禁止任何平台或机器特征**

- 理由：跨 Windows / macOS 与多平台分发，写死路径会误导（与同批安装包可移植性问题同源）。
- 落地：告知中的路径取自脚本运行时变量，不在文档里写死示例。

**决策 7：以"探测结果驱动推进"的推理链，替代执行者的主观判断（用户提议，采纳）**

- 理由：可用性探测（0B）本就存在且代价可控（单次 GET、超时 10 秒、带重试上限），把"是否继续"从**执行者的主观判断**改为**探测结果驱动的确定性链条**，是防 ERR-009 复发的最有效形态——主观判断不可靠，确定性链条可验证。
- 落地：探测可达 → 继续执行；环境型 / 配置型失败 → 记录并继续；契约型缺陷 → 阻断（既有）；**未探测 → 禁止推断，须补探测**。链条每一环的结果须落在阶段推进状态与产物上，使其可被检查。
- 代价评估：探测已存在，不新增调用类型；增量仅为规则与状态记录，代价低。风险主要来自调用频次与对外部端点的只读请求（既有行为，未扩大范围）。

**决策 8：鉴权类失败（401/403）归为配置待补，不阻断（用户裁决采纳）**

- 事实：现有判定将 4xx 一律归为契约型缺陷（仅模板化/基路径例外），故内部需鉴权的 API 探活得 401/403 时会被判为**契约型缺陷并阻断全流程**，而实际原因只是**缺凭证**——这与本次目标、以及决策 7 的推理链在"内部 API 需鉴权"场景下的可用性直接冲突。
- **语义理由（分层论证，依据既有 spec）**：DEP-AVAIL 本就是**分层**结构——`D1 connectivity` 管**端点存活 / 链路可达**（HTTP 探活），`D5 credential` 管**凭证可用**，`D2 contract` 管返回结构契约。401/403 的出现意味着 DNS 解析、TCP 连接、（HTTPS）握手与 HTTP 请求**全部成功**且服务端**给出了响应**：从 D1 的验证目标看，**端点存活、链路可达已经成立**；拿不到业务数据源于**鉴权未通过**（D5 层面），而非端点不存在或契约违反。
- **规范依据（决定性）**：探活本身是**匿名请求**（不带任何凭证），故遇 401/403 恰落在既有裁决策略的 `config missing`（"需用户提供凭据但**未配置**"）一行——该行明确规定**不否决**，记为「未配置」并提示补配置。因此现状把 401/403 判为 `contract_defect`（结构性失败并否决）**违反既有 spec**，等于把"**未能验证契约**"当成"**契约不成立**"。本次是**回到规范既有规定**（纠偏），而非引入新口径。
- 落地：在 4xx 分支中将 401/403 单独分出，归为**配置待补**——不计入失败数（因而**不拉低可用性评分**）、不触发结构性否决（因而**不阻断全流程**），并在提示中要求补凭证后重测；其余 4xx（如具体端点的 404）维持契约型缺陷判定。
- **边界（避免放宽过度）**：须区分**未提供凭证**与**凭证无效**——① 探活为匿名请求、遇 401/403 → 归配置待补（不阻断、不拉低评分），提示补凭证；② 若已声明并提供了凭证却仍被拒（凭证无效/泄漏）→ 属真正的配置或契约缺陷，**维持既有 structural 判定**。当前探活不带凭证，故本次实际只影响①。
- 边界：仅调整 401/403；不改动 2xx、5xx、超时、模板化端点等既有判定。
- 性质：属**行为变更**（既有的 401/403 会被判为契约缺陷并阻断，改后不阻断），故同步写入 `dependency-availability` 需求与评分口径说明。

## Risks / Trade-offs

| 风险 | 影响 | 对策 |
|------|------|------|
| 依赖真实不可达时仍强制执行，产生大量失败记录 | 评测产物冗长、执行耗时增加 | 失败须结构化记录为"环境限制"并汇总失败率；不逐条堆砌 |
| 环境失败可能被误读为技能缺陷 | 评分对被测技能不公平 | 现有类别已区分环境型不否决；本次**额外**要求在产物中显式标注环境限制。评分口径的进一步完善列为后续变更 |
| 告知项增加使输出变长 | 用户阅读成本上升 | 四项要素固定顺序、简洁表述；终态清单只列最终交付物 |
| 强制尝试可能触发对外部端点的真实调用 | 副作用与耗时 | 阶段 2/3 本就要求真实执行；调用范围以被测技能声明为界（既有范围契约已约束） |
| 文字约束仍可能不被遵循（ERR-009 复发风险） | 本次改进失效 | 以决策 2 的三处产物断言兜底：即使 Agent 不读约束，未完整执行也会在产物上暴露 |
| **鉴权类失败被误判为契约缺陷（401/403 → 阻断）** | 内部需鉴权 API 场景被误阻断，推理链失效 | **已消解**：按决策 8 将 401/403 归为配置待补（不阻断、不拉低评分）；残余风险为 401/403 掩盖了真实凭证配置问题，故须在提示中明确要求补凭证后重测 |
| 推理链依赖探测判定的准确性 | 判定不准会把主观测评换成"机械化误判" | 明确各类别语义与边界；鉴权类问题按决策 8 处置 |
| 终态清单纳入中间产物后输出变长 | 阅读成本上升 | 清单分组呈现：最终交付物在前，阶段卡点产物在后，缺项高亮 |
