## MACHINE_PATH_PATTERNS — 机器路径检测误报（正则字符串/举例被当硬编码）

- **ID**: ERR-008
- **标签**: `E13` `#误报`
- **状态**: active
- **发现**: 2026-09-01（源自 TASKLOG P4）
- **现象**: `MACHINE_PATH_PATTERNS` 逐行正则匹配，
  **不区分「真实写死路径」与「文档举例 / 正则字符串 / 模板说明块」**。
  实证误报：
  - `schema_from_template.py:46` —— `FIELD_RE` 正则被判为 `windows_drive`
  - `assets/report.template.md:96` —— 模板说明「如 `/Users/...`」举例被判为硬编码
- **前提/依赖**: 可移植性维度检测（质量预检 S0）
- **归因**: 边界未处理——匹配未区分「代码/文档中的路径字面量」与「真实配置的硬编码路径」
- **修改策略**:
  - 排除 `> **模板说明**` 段（`.md`）
  - 排除 `re.compile(r"...")` / `_RE = r"..."` 正则定义字符串内的匹配（`.py`）
  - 排除反引号 / 引号内举例路径
  - **保留**字符串常量中的真实硬编码路径（如 `LOG_DIR = "/Users/x/logs"`）
- **验证方式**: 上列两处实证误报消失，且真实硬编码仍能检出
- **误判史**: 无
- **⚠️ 禁止过宽排除（关键 · 防重蹈）**:
  **不可「凡在引号内都排除」**——真实硬编码多写在字符串里，过宽会漏检。
  候选仍交 LLM 复核、**不自动判级**（L123 原有设计保留），故误报风险可控。

> 与 ERR-006/007 同为「误报类」，但方向相反：
> ERR-006/007 是**漏了排除**（把非依赖当依赖），
> 本条若修过头则变成**排除过宽**（把真依赖当非依赖）。
> **修误报时的通病：只顾消除当前误报，不问是否引入反向漏检。**
