# S1 / build_sample_pack

> 阶段 S1（样本包生成）· 模块 `scripts/build_sample_pack.py`

## 评分器模板未实现各 rubric 语义，R1–R10 实为同一检查的副本

- **ID**: ERR-016
- **标签**: `E11` `#误报`
- **状态**: active
- **发现**: 2026-09-08
- **现象**: 功能任务 FT03 的 R1–R10 全部失败，理由**完全相同**：
  「Rn 未通过：缺少字段或条目为空：[]」，得分非 0 即 10，**无中间态**。
- **前提/依赖**: 功能任务 Grader 由 `_FUNC_RUBRIC_TEMPLATE` 生成
- **归因（源码实证）**: `build_sample_pack.py` 的 `_FUNC_RUBRIC_TEMPLATE`
  中，**仅 `__RID__` 为变量**，判定逻辑对全部 rubric 完全一致：

  ```python
  required = ["status", "summary", "items", "evidence", "notes"]
  ok = not missing and isinstance(data.get("items"), list) and len(data["items"]) > 0
  ```

  即：所有 rubric 实际只检查「**items 非空**」，
  **未实现各自名义上的检查语义**。
- **对照（名义 vs 实际）**:

  | rubric | 名义语义（TaskDescription） | 实际检查 | 判定 |
  |---|---|---|---|
  | R1 | result.json 有效且含必需字段 | 同左 | ✅ 一致 |
  | R2 | items 为非空数组 | 同左 | ✅ 一致 |
  | R3 | 用户可见交付 + 链接/来源标注 | items 非空 | ⚠️ 部分覆盖 |
  | R4 | 响应覆盖用户意图 | items 非空 | ❌ **被覆盖** |
  | R5 | **调用正确入口**（如 `/api/v1/hot-topics`） | items 非空 | ❌ **被覆盖** |
  | R6 | 交付用户可见产物（非脚手架） | items 非空 | ❌ **被覆盖** |
  | R7 | 不切换来源冒充 / 不执行命令（安全边界） | items 非空 | ❌ **被覆盖** |
  | R8 | capability_source 指向用户功能区 | items 非空 | ❌ **被覆盖** |
  | R9–R10 | 防编造 / 安全边界 | items 非空 | ❌ **被覆盖** |

  > **要点**：R1/R2 的设计本就是"有数据"，当前实现对它们**是正确的**；
  > 错的是 **R4–R8（来自 checks 的 5 条真实语义）及 R9–R10** 被同一模板覆盖。

- **三重后果**:
  1. **信息量为零**：10 条必然同因同果，读者无法得知哪项真没做到
  2. **过程正确的项被误判**（严重）：FT03 确实调用了正确入口
     `/api/v1/hot-topics`（`status=success`），**R5** 仍判失败——
     **用"结果为空"否定了"过程正确"**
  3. **改进建议必然为空**：模板无建议生成逻辑，报告一律显示 `—`
- **影响**: 功能任务评分**形同虚设**——声称 10 个维度，实际只有 1 个。
  据此得出的「技能缺陷」结论不可信（叠加 ERR-012/015 的归责失真）。
- **修改策略**: 待定，须人裁决（按代价递增）：
  1. **最小**：报告侧合并同因 rubric 为 1 条根因（治标，保留现评分）
  2. **中等**：让各 rubric 至少实现可判子集——
     `status` / `summary` 关键词 / 调用 URL 匹配 / 安全纪律等可用脚本判定
  3. **彻底**：把需语义判断的 rubric 交 LLM 裁定，脚本只做结构校验
- **验证方式**: 构造"调用正确但返回空"的用例，R2 应判**通过**
- **误判史**:
  - ✗ 曾以为 R1–R10 是 10 个独立维度的检查结果——实为同一检查的副本
  - ✗ **曾把 `functional_tasks.checks` 的 5 条臆断为 R1–R5**（凭顺序编号），
    据此误判"R2 被冤枉"。实读 `TaskDescription.md` 后确认：
    checks 映射的是 **R4–R8**，且 R1/R2 本就设计为"有数据"检查。
    ——与 ERR-003 同型：**凭顺序/印象推断编号，而非读实际定义**
- **关联**: 本条是 ERR-013 / ERR-015 的**更深层根因**：
  ERR-013（只给症状）与 ERR-015（归责失真）都建立在
  「rubric 是真检查」的假设上；若评分器本身未实现语义，
  则修报告格式或加归责自检都只是**在错误的地基上装修**
