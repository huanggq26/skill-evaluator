## 「约束已写但未激活」——本类失误反复出现

- **ID**: ERR-009
- **标签**: `E33` `#系统性` `#误判史`
- **状态**: active
- **发现**: 2026-09-04（P6 教训首现）／2026-09-07 复现并确认「第五次」
- **现象**: 通用规格**早有**「跨项目专题的归档归属」条款，
  但因规格目录无治理区，本次跨项目工作**全程无登记处**。
  归档原文：「**约束存在不等于生效**，这是本类失误**第五次出现**。」
- **前提/依赖**: 该条款无门禁、无载体、无触发点
- **归因**: 规范写入后**缺少使其生效的机制**（门禁脚本 / 载体目录 / 触发时机）→ 假规则
- **佐证（同源实证）**: P6 机械校验条款写进规范后、脚本未落之前同样处于假规则状态；
  脚本首跑即暴露 **13 个**规格文件声明块缺 `自检锚点` 字段
- **新增实证（2026-09-08 · 第六次）**: 通用规格 L306 **已登记**
  「锚点稳定：跨文档用标题域名、**去编号分层**」条款，但该文件自身仍保留
  **13 处**手工编号标题（`一、`/`二、`…）——**规范登记了约束，唯独豁免了自己**
- **修改策略**:
  - 写规范时**同步回答"它靠什么生效"**：门禁？载体？触发时机？
  - 无生效机制的条款 = 没写
- **验证方式**: 新增条款均配门禁，且首跑能复现预期阻断
- **误判史**:
  - ✗ 前四次均被当作"偶发疏漏"处理，未识别为同一模式 → 导致第五次

## 评测自身 reach=0：抽取兜底把中间产物当成了对外功能

> 实为抽取兜底违反功能表唯一权威定义（排除中间产物）。

## 全局 npm 包安装成功但命令不可用（bin 目录不在 PATH）

- **ID**: ERR-025
- **标签**: `E22` `E13`
- **状态**: fixed
- **发现**: 2026-09-09（OpenSpec 改造 T1.1 执行时）
- **现象**: `npm install -g @fission-ai/openspec@latest` 显示安装完成，包确实存在于全局包目录，但执行 `openspec --version` 报 `command not found`。
- **前提/依赖**: 机器存在多套 Node 环境（版本管理器 / 其他工具链自带）；`npm root -g` 指向非标准路径（本次为某工具链的 node 目录），其 bin 子目录未加入 `PATH`。
- **归因**:
  1. 默认假设"全局安装 = 命令可用"——**隐含前提失效**：仅有包目录，缺 PATH 入口
  2. 安装输出未校验命令可用性即判定"安装完成"（**验证对象错位**：验证了"安装动作"而非"可用性"）
  3. **（二次加固，用户指出）运行时归属耦合**：不止包目录属于第三方工具链——`which node` 追到底 `~/.local/bin/node -> ~/.hermes/node/bin/node`，**解释器本身也来自该工具链**。即"命令能用"是建立在他人运行时之上的，卸载该工具链即整体失效。初版符号链接方案只补了 PATH 入口，**未解除这层依赖**，属于表层修复
- **修改策略**:
  - **判定成功的标准是命令可执行**，不是安装命令退出 0——每步安装后必跑 `--version` 校验
  - 先用 `npm root -g` 确认实际全局目录，再检查其 bin 是否在 `PATH`
  - **表层修复**：在**已在 PATH 的目录**建符号链接指向包的 bin 脚本（轻量、可逆），优于改动 shell 配置
  - **根治（依赖解耦，最终采用）**：
    1. 用工具自带的 `install_binary` 装**独立 Node**（落 `~/.workbuddy/binaries/node/`，与任何第三方工具链无关）
    2. 用该 node 的 npm 重装包——全局 prefix 随之变为独立目录，不再落在他人工具链下
    3. **不用裸软链**：包内 bin 的 shebang 是 `#!/usr/bin/env node`，会解析 PATH 首个 node，仍可能绕回他人运行时；改为 **wrapper 脚本 `exec <绝对路径 node> <绝对路径 入口.js> "$@"`**，解释器路径硬编码
    4. wrapper 落在自身工具目录（如 `~/.codebuddy/bin`，已在 PATH），不动他人创建的 `~/.local/bin/node` 链接
    5. **收敛为唯一运行时**：旧运行时副本用 `trash` 移出（不 `rm`，可恢复），其原路径建**软链指向新 node**——兼容第三方对该路径的硬编码引用（如 hermes `node-bootstrap.sh` 的策略 2 兜底），使"存在的二进制"只剩一套而调用方无感知
  - **最终态（已验证 2026-09-09）**：`which node` / `~/.local/bin/node` / `~/.hermes/node/bin/node` / `CODEBUDDY_NODE_BIN` 四处全为 `v22.12.0`；`find` 真实 node 二进制仅 `~/.workbuddy/.../bin/node` 一份；`npm root -g` 指向新位置；openspec 1.12.0 与 hermes v0.14.0 均正常
  - 文档化：把"多 Node 环境时以 `npm root -g` 输出为准"写入改造方案
- **验证方式**:
  - 基础：`which openspec` 有输出 且 `openspec --version` 返回版本号
  - **解耦验证（关键）**：`env PATH=/usr/bin:/bin:<自身bin目录> openspec --version` 仍返回版本号——PATH 内无 node 也能跑，证明不依赖任何外部运行时
  - 落点核验：包目录路径不含第三方工具链名
- **误判史**: 初版判定 fixed 过早——仅验到"命令可执行"，未追问"它依赖谁"。用户以"删掉 hermes 会失效"指出耦合后才补齐第 3 层归因。**教训：修复外部依赖类问题时，验收要问依赖来源，而不只是可用性**

## 临时脚本整文件重写 — 变量残留导致目标文档被清空

- **ID**: ERR-028
- **标签**: `E22` `E33` `E32` `E03`
- **状态**: active
- **发现**: 2026-10-09
- **现象**: 用 `python3` heredoc 临时脚本对解释性文档做**整文件重写**，结果 1535 行全部变为空行，仅残留 18 行非空，且**无任何报错**。目标文件位于工作区外（CloudDocs），无版本控制。
- **前提/依赖**:
  - 目标为**工作区外的长期资产**，不随项目备份自动覆盖
  - 采用整文件重写（`write_text` 全量替换），而非精确匹配替换
  - 写入前无体积/非空行守卫，编辑前未备份
- **归因**:
  1. 脚本循环内误写 `out.append(l)`——`l` 是**上一次 for 循环残留的变量**（值为空串），正确应为 `lines[i]`（直接原因）
  2. 采用整文件重写，一处变量错误即污染全文，无局部化边界（放大原因）
  3. 部分 `.replace()` 未加 assert，未命中时**静默跳过** → 后续重复插入产生重复小节（同源缺陷）
  4. 未使用编辑工具的精确匹配与失败保护；编辑前未备份
- **修改策略**:
  - 优先使用编辑工具的精确替换（唯一性校验、失败即报错）；确需脚本时**每个替换必须 assert 命中**
  - **写入前置守卫**：新内容非空行数或体积低于原文件 90% 即中止并报错
  - **原子写**：临时文件 → 校验 → 替换
  - **编辑前备份**至 `.project/backup/`，命名 `<目标>-pre-<动作>-<时间戳>.md`
  - 循环内**禁止**使用外部残留变量，一律显式索引
  - 已并入治理规格 `Specs/project_spec_maintenance.md`「整文件重写的守卫（脚本写盘的补充约束 · 强制）」；并固化为治理脚手架 `.project/tmp/govkit.py`（优先调用，不手工操作）
- **验证方式**: 脚本守卫输出「非空行 A → B」且无骤降；事后核对 `wc -l` 与关键章节标题数；确认备份文件存在
- **误判史**:
  - ✗ 一度认为"备份只需要项目级备份即可"——实际缺单次编辑前备份，致事故几乎不可恢复（靠用户手工副本挽回）
