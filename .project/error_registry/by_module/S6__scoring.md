## 凭印象猜字段名，断言 rubric 数为 0

  实际字段名并非 `rubrics`，而是 **`checks`**——**断言的前提就是错的**。
- **前提/依赖**: 未读取实际 JSON 结构，仅凭字段名记忆推断

- **误判史**:

## 增量能力「交付即满分」，评分无质量维度与区分度

- **ID**: ERR-023
- **标签**: `E32` `E13`
- **状态**: fixed
- **发现**: 2026-09-08（用户审读 aihot 报告 §4 质疑：「不管 baseline 成败都是 100 分」）
- **现象**: aihot 整合表 7 行任务评分全部 100.00——评分列零信息量。
  溯源：10 条任务全部走 incremental_utility 路径（baseline 屏蔽私有 API 后不可达），
  而该路径「交付了」即 100 分，**8/10 达标（threshold=8 即 pass）与 10/10 得同样的满分**。
- **归因**:
  1. task_score 三分支公式（spec_contract）中增量分支只看成败状态、不看交付质量——
     rubric 通过率数据（`with_skill_passed_checks`）已在 Tasks.json，但评分未消费
  2. 阈值判定（8/10 即 pass）把 8/9/10 全归为同一成功态，两极化抹平了中间质量
  3. 本质是**评分模型的区分度缺陷**：分数的用途是区分，全同分 = 该维度失效
- **连带发现（方法学，未修）**: 增量判定依赖 baseline 屏蔽策略——aihot 的 API 是
  公开匿名只读的，「裸 Agent 屏蔽后做不到」测出的是「知识不对称增量」而非纯「能力增量」。
  公开 API 算不算技能私产牵动所有 API 型技能的增量判定，**单独立项讨论**（用户裁定 C 不动）
- **修改策略（已实施 2026-09-08，用户裁定 A+B）**:
  - **B 评分模型**：增量分支改 `100 × rubric 通过率`
    （`with_skill_passed_checks / total_checks`，数据缺失兼容 100）；
    spec_contract.md 与 scores.spec.md 契约同步更新
  - **A 呈现层**：整合表/验证表列名「任务评分」→「任务价值分」；
    §4 引导语补口径说明（增量=满分×质量，可比=效能分，失败=0）
- **验证结果**:
  | 用例 | 结果 |
  |---|---|
  | 单元：8/10 → 80、9/10 → 90、10/10 → 100、缺失 → 100 兼容 | ✓ 区分度恢复 |
  | aihot 重跑 | 全 100（**真实满分**：10 条均 10/10），门禁不变 |
  | skill-evaluator 重跑 | 未实测行「—」不受影响，门禁不变 |
- **误判史**: 无（用户审读发现）

## R1–R10 评分器是同一份结构校验的十份拷贝，10/10 ≠ 质量满分

- **ID**: ERR-024
- **标签**: `E32` `E09`
- **状态**: fixed（aihot 已生成语义判据；其余样本待生成）
- **发现**: 2026-09-08（用户追问「还是都 100 分，是你的预期吗」→ 查证 grader 实现）
- **现象**: aihot 全部任务 10/10 通过、任务价值分全 100。查证发现
  `R1.py`–`R10.py` **内容完全相同**，判定逻辑只有一句：
  检查 result.json 含 `status/summary/items/evidence/notes` 且 items 非空。
  → 10/10 的含义是「产物 JSON 结构合规」，与交付质量无关。
- **归因**:
  1. `build_sample_pack._FUNC_RUBRIC_TEMPLATE` 是**通用脚手架**——它不认识被测技能，
     只能做结构校验；而同一脚本的 `_TASKDESC_TEMPLATE` **已明确规定** R1–R10 的
     语义分工（R1–R3 基础合规 / R4–R8 功能验证 / R9–R10 质量保障）——**设计与实现脱节**
  2. 语义判据本应由 AI 依据每个任务的 objective/checks 编写（同 function_table 需 AI 裁定），
     但这一环节**从未实现**，脚手架模板被直接当作评分器使用
  3. 与 **ERR-018 同构**：抽取兜底把产出物当功能；此处把结构校验模板当语义评分器
     ——**都把占位当实质**
- **修改策略（已实施 2026-09-08，用户裁定 先 b 后 a）**:
  - **a 治本**：新增 `scripts/gen_semantic_rubrics.py`，为每个任务生成 10 个**语义不同**
    的判据（structure/completeness/deliverability/endpoint/params/relevance/
    no_placeholder/volume/anti_fabrication/safety），参数**全部取自任务自身声明**
    （objective / checks / 默认请求），不硬编码任何技能域名
  - **b 止损**：`generate_outputs` 检测 `grader_manifest.rubric_mode`，模板态在 §4
    明示「分值仅代表结构合规，不代表交付质量」并给出生成命令；语义态标注自动消失
- **实施踩坑 6 则（全部留档）**:
  1. f-string 嵌套：生成代码里的 `{len(ev)}` 被外层 f-string 吃掉 → 须 `{{...}}`
  2. return 后多写 `)`（return 直接跟字典，不是函数调用）→ 10 个文件全语法错误
  3. manifest 的 type 误用循环变量 `kind` → 10 项全写成同一类型（须 `rubrics[rid][0]`）
  4. 端点提取：aihot「默认请求：/api/...」**无反引号**，首版全 N/A → 正则须兼顾两种写法
  5. 关键词噪音：疑问词「有什么」、引导语「明确说"」→ 在 items 里永远命中不了，
     会把相关性判据变成**恒定失败的假阴性** → 加弱关键词降级
  6. 字面匹配局限：中文「日报」vs 英文 `dailies/latest` → 来源已验证即降级通过
     （相关性由来源保证，不苛求字面）
- **验证结果**:
  | 用例 | 结果 |
  |---|---|
  | aihot 10 条生成语义判据 + 重跑 grader | FT04 = 9/10（端点证据缺失，真实问题），其余 10/10（来源已验证） |
  | 报告区分度 | 事件追踪 100 → **90.00**；overall 100 → **99.0** |
  | 模板态标注 | 自评样本标注出现 / aihot（semantic）标注消失 |
  | 门禁 | 仍为「推荐上架」（1 项证据瑕疵不构成降档） |
