**关键决策**：

- **主线用自愈**：原始动机是"AI 如何归因、找根因、自动自愈"，该主线能让全部策略产生因果；结构为 是什么 / 怎么用 / 如何进化 三层，标题不带字母标号。
- **规格目录不设治理区**：元规格为规则定义者，套用治理会自指（上层受下位约束），逻辑不自洽；其"为什么"由规格文件自身的决策锚点承载，不依赖外部任务文件。
- **单一锚点记录**：跨项目 / 一次性工作一律记入**当前打开项目**的 TASKLOG，用 `[涉外部]` / `[一次性·非本项目]` 标注，**不做跨项目拆分、不双记**。

**验证**：编号 0、标题引号 0、Mermaid 引号 0、LR 图 0、lint 干净。

**教训**：

1. **需求出发点三次误判**——我从"机制完备性"出发（跨项目可见性 / 双记 / 记得在哪个项目），用户从"实际工作流"纠正（恢复上下文 / 单一锚点 / 项目即上下文边界）。结论：**实际工作流优先于机制完备性**——更完备的方案若执行时易漏，效果不如简单方案。
2. **"已写但未激活"再次复现**——通用规格早有「跨项目专题的归档归属」条款，但因规格目录无治理区，本次跨项目工作全程无登记处。**约束存在不等于生效**，这是本类失误第五次出现。
3. **载体分工原条款过宽**——"用 Mermaid 不用文本配图"把目录树也禁了。正确判据是**包含关系用文本树、流转关系用 Mermaid**（能被复制走的用文本，需要看懂关系的用图）。
4. **项目即上下文边界**——切换项目时，离开前落盘、进入后只读当前项目，"记得当时在哪个项目"不是必要负担，因为切换动作本身即选择上下文。此机制已固化进两层规格。
