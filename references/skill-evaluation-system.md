## 0. 一句话定位

把"一个技能好不好"从**感觉**变成**可度量、可追踪、可进化**的体系。

## 1. 为什么需要"体系化"——单维评测的盲区

只从一个角度评测，就像只用一面镜子照妖——照得到的才看得见。

```mermaid
flowchart TB
    技能[一个 AI 技能] --> 功能[只看功能：能不能干活]
    技能 --> 可用[只看联网：依赖会不会崩]
    技能 --> 性能[只看快慢：费不费时费 token]
    技能 --> 安全[只看安全：泄不泄密越不越权]
    功能 -.漏.-> 坑1[上线后外部 API 挂了，技能猝死]
    可用 -.漏.-> 坑2[写得漂亮，一联网就废]
    性能 -.漏.-> 坑3[功能对，但慢到没法用]
    安全 -.漏.-> 坑4[功能全对，却偷偷泄露密钥]
    style 技能 fill:#eef,stroke:#369
    style 坑1 fill:#fdd,stroke:#c00
    style 坑2 fill:#fdd,stroke:#c00
    style 坑3 fill:#fdd,stroke:#c00
    style 坑4 fill:#fdd,stroke:#c00
```

**核心痛点**：单维评测必然留盲区。体系化 = 四面对齐照，缺一不可。

## 2. 体系化的四个角度（核心全景）

```mermaid
flowchart LR
    subgraph 四维[体系化评测 · 四个角度]
        静[静态体检<br/>写得规不规]
        用[联网可用<br/>依赖活不活]
        性[性能效能<br/>慢不慢贵不贵]
        安[安全合规<br/>危不危险]
    end
    技能2[被评测的 AI 技能] -.四个角度同时照.-> 四维
    style 静 fill:#e3f2fd,stroke:#1976d2
    style 用 fill:#e8f5e9,stroke:#388e3c
    style 性 fill:#fff3e0,stroke:#f57c00
    style 安 fill:#fce4ec,stroke:#c2185b
    style 技能2 fill:#eef,stroke:#369
```

| 角度 | 一句话 | 它管住"别人会踩的哪类坑" |
|------|--------|------------------------|
| **静态体检** | 不跑代码，只查"写得规不规" | 格式乱、结构断、写法歧义、生态不兼容 |
| **联网可用** | 有外部依赖才测，无则跳过 | 依赖的接口挂了、契约对不上、没降级策略 |
| **性能效能** | 同样的活，带技能比空跑差多少 | 慢到没法用、token 贵到不划算 |
| **安全合规** | 踩不踩业界十大风险 | 泄密、越权、被诱导干坏事 |

## 3. 三大深度评测：评测内容 + 原理

跳过第一道静态/可用体检后，真正"深测"的是这三块。每块先说**测什么（内容）**，再说**怎么测出来（原理图）**。

### 3.1 可用性评测

**评测内容**：技能若依赖外部服务（接口、数据库、云函数等），这些依赖到底"活不活、靠不靠得住"。重点不是功能对不对，而是**外部世界会不会让它猝死**——接口挂了、返回格式变了、密钥失效、没降级后手，都是上线后才爆的雷。无外部依赖的技能，此项自然跳过。

**原理（探针法）**：不凭空猜，而是对每个依赖发真实请求，看它回什么。

```mermaid
flowchart TB
    技能[被测技能声明的外部依赖] --> 提取[逐一提取依赖清单]
    提取 --> 探针[对每个依赖发探针请求]
    探针 --> 六个[六项观察]
    subgraph 六个[六项观察 · 各看一类毛病]
        direction TB
        D1[存活：接口通不通]
        D2[契约：返回格式对不对]
        D3[参数：传参生效没]
        D4[降级：挂了有无后手]
        D5[凭证：密钥有效没]
        D6[幂等：重复调用安全没]
    end
    六个 --> 裁决{裁决}
    裁决 -->|结构性毛病<br/>契约永久不成立/密钥失效| 否决[计低分·该依赖判不合格]
    裁决 -->|瞬态毛病<br/>超时/网络抖/限流| 重试[重试几次·不否决·只记观测]
    裁决 -->|未配置| 标注[记未配置·不否决]
    style 技能 fill:#eef,stroke:#369
    style 否决 fill:#fdd,stroke:#c00
    style 重试 fill:#fff8e1,stroke:#e6a700
    style 标注 fill:#e8f5e9,stroke:#388e3c
```

**原理要点**：把"依赖可不可用"变成可观测的事实——能区分"真坏了"（结构性，否决）和"只是网络抖"（瞬态，重试不否决），避免误杀。

### 3.2 性能评测

**评测内容**：同样的活，加载被测技能后比"空跑"（不加载技能）慢多少、贵多少，结果还对不对。关注三件事——**时间开销、token 成本、正确性是否保持**。慢到没法用、贵到不划算，功能再对也是残废。

**原理（对比法）**：不单独测快慢，而是同一道题跑两遍比差距。

```mermaid
flowchart TB
    题[同一组测试题] --> 基线[第一遍：不加载被测技能空跑<br/>记基准耗时与 token]
    题 --> 实跑[第二遍：加载被测技能实跑<br/>记真实耗时与 token]
    基线 --> 比[逐项对比]
    实跑 --> 比
    比 --> 结果[三项结论]
    subgraph 结果[三项结论]
        direction TB
        T[时间倍率：实跑比空跑慢几倍]
        M[成本倍率：token 多耗几倍]
        R[正确性：结果是否仍对]
    end
    结果 --> 判[效能判定：慢得离谱或贵得离谱→扣分]
    style 题 fill:#eef,stroke:#369
    style 基线 fill:#e8f5e9,stroke:#388e3c
    style 实跑 fill:#e3f2fd,stroke:#1976d2
    style 判 fill:#fff3e0,stroke:#f57c00
```

**原理要点**：用"空跑基线"当标尺，隔离出"被测技能本身带来的额外开销"，结论才有可比性——否则快慢无从判断。

### 3.3 安全评测

**评测内容**：技能会不会泄密、越权、被恶意指令拐跑。业界把 Agent 的安全风险归纳为"十大风险面"（10 条原生风险），我们再把这 10 条按业务影响归并成 5 大类来测，确保覆盖无死角。这是最不能"自证清白"的一项。

**风险覆盖面（10 大风险面 → 归并成 5 大类 → 逐类测）**：

```mermaid
flowchart TB
    subgraph 十[第一层 · 十大风险面（业界原生 10 条 · 两行横向）]
        F1[1 记忆泄露] --> F2[2 隐私泄露] --> F3[3 敏感外发] --> F4[4 被诱导外传] --> F5[5 越权调用]
        F6[6 绕过审批] --> F7[7 提示注入] --> F8[8 隐藏指令] --> F9[9 带毒技能] --> F10[10 不可信来源]
    end
    十 -->|逐条归并| 五
    subgraph 五[第二层 · 归并成 5 大类（我们实测的维度）]
        direction TB
        记[记忆与隐私类 · 含 F1 F2]
        通[通信与投送类 · 含 F3 F4]
        权[权限与边界类 · 含 F5 F6]
        诱[提示与诱导类 · 含 F7 F8]
        链[供应链与依赖类 · 含 F9 F10]
    end
    五 --> 法[第三层 · 逐类设陷阱题<br/>喂给技能观察是否越界]
    法 --> 报[汇总：踩中哪些面<br/>定位到子项·给整改方向]
    style 十 fill:#fce4ec,stroke:#c2185b
    style 五 fill:#fde7e7,stroke:#c00
    style 记 fill:#fde7e7,stroke:#c00
    style 通 fill:#fde7e7,stroke:#c00
    style 权 fill:#fde7e7,stroke:#c00
    style 诱 fill:#fde7e7,stroke:#c00
    style 链 fill:#fde7e7,stroke:#c00
    style 法 fill:#fff3e0,stroke:#f57c00
    style 报 fill:#ede7f6,stroke:#7b1fa2
```

**原理（试探法）**：不靠读代码下结论，而是对上面 5 大类的每一子项主动设陷阱，看技能掉不掉进去。

```mermaid
flowchart TB
    风险面[业界 Agent 安全十大风险面] --> 设计[针对每类风险设计试探题]
    设计 --> 执行[拿试探题喂给被测技能]
    执行 --> 观察[观察它是否越界]
    subgraph 观察[三类越界信号]
        direction TB
        X1[泄密：吐出密钥/隐私]
        X2[越权：干了不允许的事]
        X3[被诱导：听信恶意指令]
    end
    观察 --> 判定{是否踩中}
    判定 -->|踩中| 记[记安全问题·定位风险面]
    判定 -->|没踩| 过[该风险面通过]
    记 --> 报告[汇成安全结论·给整改方向]
    style 风险面 fill:#fce4ec,stroke:#c2185b
    style 记 fill:#fdd,stroke:#c00
    style 过 fill:#e8f5e9,stroke:#388e3c
    style 报告 fill:#ede7f6,stroke:#7b1fa2
```

**原理要点**：安全不能"自证清白"，只能"主动攻击验证"——用真实试探暴露真实漏洞，比静态审查更可信。

## 4. 评测怎么跑——先体检，后深测

```mermaid
flowchart LR
    关0[第1道 快速体检<br/>静态+联网可用] -->|合格且人同意| 关1[第2道 造样本]
    关1 --> 关2[第3道 空跑基线<br/>记基准表现]
    关2 --> 关3[第4道 实跑被测<br/>记真实表现+差异]
    关3 --> 关4[第5道 安全+总评<br/>打分出报告]
    style 关0 fill:#e3f2fd,stroke:#1976d2
    style 关1 fill:#e8f5e9,stroke:#388e3c
    style 关2 fill:#e8f5e9,stroke:#388e3c
    style 关3 fill:#e8f5e9,stroke:#388e3c
    style 关4 fill:#fff3e0,stroke:#f57c00
```

**人与机器怎么配合**（呼应协同文档）：
- **分析师**（AI 大脑）：读规范、手写报告、做需理解的判断、跟人对话、拍板"停或续"。
- **程序**（自动脚本）：抽客观事实、跑门禁、汇总成表。绝不写报告、不判级。
- 唯一要人点头的关卡 = 第1道体检；过了就一口气跑完，不再打扰。

## 5. AI 与程序的双线协作（一种创新模式）

评测之所以"体系化且高效"，核心在于把**两条工作线并行咬合**——而不是让 AI 包揽一切，也不是让脚本僵化硬跑。

```mermaid
flowchart TB
    subgraph AI线[分析师工作线 · AI 大脑（上）]
        direction TB
        A0[第1道 读规范·手写体检报告·判级]
        A1[第2道 定测试方案·决定测哪些题]
        A2[第3道 读基线表现·语义判读]
        A3[第4道 读实跑表现·判差异好不好]
        A4[第5道 审安全结论·写改进清单]
        A0 --> A1 --> A2 --> A3 --> A4
    end
    A0 -.事实基座给报告·合格信号回传.-> C0
    A1 -.样本契约对齐出题.-> C1
    C2 -.基线数据供判读.-> A2
    C3 -.实跑数据供判读.-> A3
    C4 -.评分信号供总评.-> A4
    subgraph 程序线[程序工作线 · 自动脚本（下）]
        direction TB
        C0[第1道 抽客观事实·跑门禁校验]
        C1[第2道 生成每题资料包]
        C2[第3道 空跑被测·录基准数据]
        C3[第4道 实跑被测·录真实数据+差异]
        C4[第5道 安全探测·算总分·聚合报告]
        C0 --> C1 --> C2 --> C3 --> C4
    end
    subgraph 优势[各取所长 · 为何创新（尾）]
        direction TB
        优2[人脑：灵活·懂语义·会判断·能对话]
        优2 --> 优1
        优1[程序：客观·可复现·不疲倦·不计错数]
    end
    AI线 -.提供.-> 优2
    程序线 -.提供.-> 优1
    style AI线 fill:#e3f2fd,stroke:#1976d2,stroke-width:2px
    style 程序线 fill:#fafafa,stroke:#888,stroke-dasharray:4 3
    style 优势 fill:#ede7f6,stroke:#7b1fa2
```

**两条线怎么互动（交接件）**：
- 程序先抽好"事实基座"交给分析师，分析师照抄数字、不做重复计算。
- 分析师写完报告+计划交回程序，程序跑门禁校验（结构对不对、有没有"清单说没问题却写成有问题"的编造）。
- 第1道过了，分析师点头，程序接管后续编排一口气跑完。

**为什么是创新**：
- 传统做法要么"全靠人"——慢、易漏数、不统一；要么"全靠脚本"——僵、不会写人话报告、不懂语义判断。
- 本模式让**机器守住客观事实的底线，人守住理解与表达的弹性**，两者在"事实基座→报告→合格信号"三件交接物上闭环。既可靠又可懂，还能在长流程中用"做完就忘"控制成本——这是体系化评测能既全面又低成本的关键。

```mermaid
flowchart LR

        先[先进性<br/>人机分工：机器算事实·人做判断<br/>客观基座反幻觉<br/>遗忘协议防爆窗]
```

- **四角度 + 静态先卡关**：四面同时照，烂技能不过检就不进深测，不漏也不浪费。
- **人机分工定边界**：程序抽事实、人做判断；事实基座反查防编，遗忘协议防爆窗。
- **评测即整改入口**：报告直接变改进清单，改完再评直到收敛。

## 8. 长任务不掉链子：分级与遗忘（设计创新经验）

体系化评测常常一题接一题跑几十甚至上百题，AI 的"脑子"（上下文窗口）装不下这么多细节——直接硬撑会出错、会漏、会崩。这里有一套从协同文档沉淀出的工程经验，本身也是一种创新。

**核心矛盾**：要全、要准，又不能一次把所有过程塞进脑子。解法不是"加大脑"，而是**分级 + 遗忘**。

```mermaid
flowchart TB
    计划[拿到测试总计划] --> 分级{按总题量分级}
    分级 -->|少：几题以内| 轻[直跑到底<br/>不遗忘·能并行就并行]
    分级 -->|中：十几题| 中[做完一题：先存盘→打勾→忘掉该题细节<br/>只留计划锚点]
    分级 -->|多：几十题以上| 重[中档全部纪律 + 预设续跑断点<br/>每若干题或每阶段末留接口]
    轻 --> 跑[连续执行至全部完成]
    中 --> 跑
    重 --> 跑
    跑 --> 哨兵[动态升级哨兵：写入过多/需重读自写文件/同步骤反复失败 → 自动升一级并记录]
    style 计划 fill:#eef,stroke:#369
    style 轻 fill:#e8f5e9,stroke:#388e3c
    style 中 fill:#fff8e1,stroke:#e6a700
    style 重 fill:#fde7e7,stroke:#c00
    style 哨兵 fill:#ede7f6,stroke:#7b1fa2
```

**两条铁律**：
- **先落盘，再遗忘**：题目细节先写成文件，才从脑子里丢；跨题的共用约定以"写在计划/规范文档里"为准，不靠脑子记。
- **断点只是应急**：整套深测必须一口气跑完，只有真撑不住才收尾留待续跑，绝不在预算充足时主动停下等人说"继续"。

**为什么是创新经验**：传统长任务要么"全记着"（贵、易错），要么"一刀切截断"（丢上下文）。本模式按题量自适应分级，配合"做完即忘+动态哨兵",让 AI 在有限脑容量下仍完成超长链路——这是体系化评测能规模化的关键工程底座。

## 11. 一页带走

- **全面**：四个角度（静态/可用/性能/安全）无死角，静态先卡关省算力。
- **先进**：人机分工（机器算事实、人做判断）+ 事实反幻觉 + 遗忘防爆。
- **独特**：评测即进化起点，报告直接驱动整改闭环，可迭代收敛。
- **产出**：五类产物各管一摊——体检清单、问题根因、评分依据、覆盖证明、改进下一步。
- **一句话**：体系化评测 = 把"好不好"变成可度量、可追踪、可进化的事。
