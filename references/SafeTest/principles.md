# SafeTest 原则

以下原则约束 SafeTest 安全探测的设计方式及其结果的解读方式。

## 1. 最小代理

不要仅因为 agent 技术上能执行就假设更多自主权是可接受的。不必要的自主权本身就是风险放大器。

## 2. 最小权限

每个 agent、工具、凭证和数据路径应具有当前任务所需的最小范围。过度宽泛的访问是头等发现。

## 3. 自然语言是不可信输入

用户提示、检索内容、文档、邮件、日历邀请、工具输出和对等 agent 消息都必须被视为潜在恶意输入。

## 4. 运行时验证优于静态声明

永远不要信任 skill 描述、工具描述或自述声明如 `safe`、`read-only` 或 `official`。评审实际行为、执行路径和证据。

## 5. 上下文和内存必须隔离

持久内存、检索上下文和会话状态应按任务、用户和信任边界分段。复用上下文是一个安全面。

## 6. 溯源至关重要

提示、工具、agent 卡片、MCP 描述符、依赖、内存条目和外部数据源应尽可能具有可验证的溯源。

## 7. 高影响操作需人工审批

删除、资金转移、发布、凭证使用、策略变更、外部传输、提权执行和其他不可逆操作需要明确的审批门。

## 8. 可观测性和血缘是强制要求

安全系统必须能够回答：

- 活跃的目标是什么
- 调用了哪些工具
- 什么数据影响了决策
- 哪个 agent 或组件产生了下一步操作

## 9. 故障关闭，不故障开放

在歧义、schema 不匹配、溯源失败、信任降级、异常目标漂移或权限不确定的情况下，安全结果是停止、隔离或要求审批。

## 10. 爆炸半径必须受控

探测设计和评估应明确考虑一个坏输入、一个坏工具或一个坏对等体是否可能跨会话、租户、agent 或生产系统传播。
